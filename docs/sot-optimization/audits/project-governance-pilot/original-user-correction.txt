6. IMPLEMENTIERUNGSPLAN LAUFEND AKTUELL HALTEN
Das Fachmodul ist während der gesamten Umsetzung das vollständige Execution Backlog dieses Epics.
Jedes Work Item erhält einen Status:
- TODO
- READY
- IN_PROGRESS
- BLOCKED
- DONE
Erledigte Items bleiben sichtbar und werden durchgestrichen:
- [x] ~~WI-xxx – Beschreibung~~
Laufende Items:
- [ ] IN_PROGRESS – WI-xxx – Beschreibung
Blockierte Items:
- [ ] BLOCKED – WI-xxx – Grund
Keine erledigten Punkte löschen.
Wenn neue notwendige Arbeit entsteht:
- neues Work Item in denselben Plan aufnehmen;
- Dependency angeben;
- priorisieren;
- Counter neu berechnen.
Keine versteckte Arbeit außerhalb des Plans.

9. PARALLELE WORKER AKTIV NUTZEN
Unabhängige Work Items dürfen und sollen parallel bearbeitet werden, wenn dadurch die Gesamtdauer sinkt.
Parallelisierung nur wenn:
- keine gleichen Dateien gleichzeitig verändert werden;
- keine konkurrierenden Planabschnitte verändert werden;
- keine offenen gegenseitigen Dependencies bestehen;
- keine konkurrierenden Architekturentscheidungen entstehen;
- Contracts klar sind;
- Merge-Reihenfolge bekannt ist.
Vor Start:
CLAIMED_BY: <worker>
Jeder Worker erhält:
- Work Item
- Scope
- erlaubte Dateien
- verbotene Dateien
- Dependencies
- erwartetes Ergebnis
- notwendige Checks
Kein Worker arbeitet außerhalb seines Claims.
10. FAST CHECK IST DER NORMALE PRÜFMODUS
Nicht jedes Work Item benötigt einen Full Check.
Der Impact-Mechanismus entscheidet zwischen:
- NO_CHECK
- FAST_CHECK
- FULL_CHECK
Normalfall
FAST_CHECK
prüft ausschließlich:
- tatsächliches Delta
- direkt betroffene Module
- relevante Contracts
- direkte Dependencies
- relevante Traceability
- relevante Tests
- Referenzen
- git diff --check
Ergebnis:
FAST_CHECK_PASS
oder
FAST_CHECK_BLOCKED
Kein globaler Scrum-Audit.
FULL CHECK
Nur bei Eskalationskriterien:
- Scrum-Core-Änderung
- Definition of Done
- Statusmodell
- zentrale Governance
- Security/Auth
- Cross-Domain
- Contract-Bruch
- mehrere Kernmodule
- unklarer Impact
- erkannte Inkonsistenz
Dann:
⚠ FULL CHECK REQUIRED
Auch dieser Check bleibt impact-basiert und wiederholt nicht automatisch die historische Scrum-Migration.

LEGACY_AUSBAUPLAN_COVERAGE_GAP
ausweisen und Impact bestimmen.
13. GIT-HYGIENE
Reihenfolge für diese Korrektur:
1. Git-Status prüfen.
2. Nur die zuletzt hinzugefügten ca. 494 SoT-/Optimierungszeilen aus ausbauplan.md entfernen.
3. Historischen Altbestand unverändert lassen.
4. Autoritatives Fachmodul anlegen.
5. Vollständige Implementierungsliste dorthin übernehmen.
6. Minimalen Epic-/Story-Verweis in docs/scrum-plan.md ergänzen.
7. FAST CHECK durchführen, sofern keine Core-Regel semantisch verändert wird.
8. Diff gegen Golden Baseline prüfen.
9. git diff --check.
10. Tests/Referenzen prüfen.
11. Danach sauber committen.
Commits:
- klein
- logisch
- nachvollziehbar
- möglichst Work-Item-bezogen
Keine Misch-Commits.
Parallele Worker bevorzugt:
- getrennte Worktrees/Branches
- oder garantiert disjunkte Dateien
nutzen.
14. DANACH AUTOMATISCH MIT DER EIGENTLICHEN UMSETZUNG FORTFAHREN
Sobald:
- ausbauplan.md sauber bereinigt ist;
- das historische Migrationsverhältnis geklärt ist;
- das autoritative Fachmodul existiert;
- der minimale Scrum-Epic-Verweis integriert ist;
- Golden Baseline weiterhin geschützt ist;
- FAST CHECK bestanden ist;
nicht auf eine weitere Nutzeranweisung warten.
Beginne mit:
Phase 1 – Requirements Preservation
danach:
FAST MERGE CHECK
und anschließend, sofern kein echter Nutzerblocker besteht:
Wave 1 – Performance Enablement
Reihenfolge zunächst:
1. Module Registry
2. Contracts
3. Dependency / Impact Graph
4. FAST CHECK Engine
5. FULL CHECK Escalation
6. Baselines
7. Delta Detection
8. Incremental Audit
Danach erst:
Wave 2 – SoT Governance
sodass die SoT-Implementierung bereits von der schnelleren Infrastruktur profitiert.
Nach jedem Item:
- Plan aktualisieren
- DONE durchstreichen
- Counter aktualisieren
- Next Recommendation bestimmen
- Parallel Candidates bestimmen
- automatisch weiterarbeiten, solange kein echter Nutzerblocker besteht.
